# دور ۸: کارایی و فضای ذخیره‌سازی با داده بزرگ

## سرعت
- **داده آزمایشی:**
  - ۵۰۰۰ رکورد آرشیو در ۳۰ شرکت (۲٫۱ میلیون نویسه)؛
  - ۶۰۰ آیتم پرونده فنی، هر کدام با ۱۰ نسخه تاریخچه (۲ میلیون نویسه).
- **شرایط:** Chromium موبایل، CPU چهار برابر کندتر (شبیه گوشی میان‌رده).

| کار | زمان |
|---|---|
| باز شدن برنامه تا صفحه ورود | ۴۸۸ ms |
| رفتن به آرشیو (فهرست + گزارش ماهانه) | ۱۴۳ ms |
| گزارش ماهانه (`monthlyData`) | ۶۷ ms |
| «نمایش بیشتر» | ۱۰۷ ms |
| پیش‌نمایش پیام تردد | ۱۰ ms |
| پرونده فنی یک شرکت | ۳۴ ms |
| هر حرف در جستجوی سراسری | ۴۸ تا ۵۸ ms |
| تاریخچه آیتم / گزارش تغییرات | ۴۷ / ۷۷ ms |

همه زیر ۱۵۰ میلی‌ثانیه؛ رفع لازم نبود.

## یافته‌ها
| # | یافته | شدت | رفع |
|---|---|---|---|
| 1 | **با حافظه پر، رکورد تازه از دست می‌رفت** («⚠️ حافظه پر است؛ رکورد ذخیره نشد»)، در حالی که کپی کامل پیش از به‌روزرسانی (یک نسخه دوم از همه داده) دست‌نخورده می‌ماند. با آرشیو بزرگ، برای جا باز کردن رکوردهای قدیمی آرشیو هم حذف می‌شد. | بالا | `storeItem()`: اول کپی پیش از به‌روزرسانی پاک می‌شود و دوباره تلاش می‌شود. برای آرشیو، پرونده فنی و حساب‌ها. |
| 2 | کپی پیش از به‌روزرسانی برای همیشه نصف فضا را می‌گرفت. | متوسط | ۳۰ روز بعد خودکار پاک می‌شود. |
| 3 | کاربر نمی‌دانست حافظه کی پر می‌شود. | متوسط | در تنظیمات (پایین آرشیو): «فضای استفاده‌شده: N٪»؛ از ۸۰٪ هشدار و راهنمای پشتیبان‌گیری. |

بازتولید: `tests/e2e/storage-quota.js` روی نسخه قبل ۷ شکست داد (رکورد تازه ذخیره نشد و کپی ماند)؛ روی نسخه جدید ۹ از ۹ قبول.

## برای بعد (به تأیید مالک)
تاریخچه پرونده فنی فقط-افزودنی است و تا ابد بزرگ می‌شود. برای چند سال استفاده سنگین، داده بزرگ باید به IndexedDB (چند صد مگابایت) یا به سرور برود. این تغییر ساختار ذخیره است و جدا برنامه‌ریزی می‌شود.

همه ۱۸ فایل تست سبز.
